# ADR 0003: Canonical root-input profile (D1, v1)

## Status

Proposed (D1, issue #3). Freeze once reviewed by a protocol reviewer other than
the author. Builds on ADR 0002 (integration branch). Does not supersede ADR 0001.

## Context

The prototype's Engine API adapter already turns a Unicity Certificate into
EVM block-building parameters (`engineapi/params.go`), but its derivation was
written for a single-shard fake and diverges from the repaired specification in
ways that matter once a second implementation (the reth fork's privileged call,
an offline verifier) has to agree byte-for-byte:

- domain separation by one-byte prefix + raw concatenation, not ASCII domain +
  CBOR;
- keyed by `(UnicityTreeRoot, shardRound)`, not `(rootRound, shardRound)`;
- no `extraData` input commitment at all;
- no signature-free "root origin" concept — nothing pins that alternate valid
  signature subsets for the same statement must yield the same execution input;
- no explicit rule that the authorizing certificate is chosen by *which round it
  authorizes*, not by local arrival order.

D1 is the gate that fixes this before any `F*` implementation.

## Decision

Adopt **profile version v1** as specified in
[`docs/design/d1-canonical-root-input.md`](../design/d1-canonical-root-input.md).
Key points:

1. **Signature-free root origin `O_-`.** Certificates and their signature sets
   are authentication witnesses only. `O_-` is a deterministic CBOR body built
   from committed content (network, root round/epoch, reference time, Unicity
   Tree root, certified `IR`, `TRHash`, `ShardConfHash`). Different valid
   signature subsets or transport encodings of the same statement produce a
   byte-identical `O_-`.

2. **Canonical `rootInput` tuple** `(v, α, β, σ, n, e, h_parent, O_-, TE_-, D)`,
   committed in the block header as `extraData = SHA-256(CBOR(rootInput))`. Every
   field a historical replay needs is inside the tuple; nothing is read from
   node-local state.

3. **Two hash worlds stay apart.** Unicity SHA-256/CBOR for commitments and
   derived fields; Ethereum Keccak-256/RLP for the block hash and parent hash.
   Ethereum digests ride inside `rootInput` as opaque byte strings.

4. **Domain-separated derivations** use `SHA-256(CBOR([DOMAIN, r, n]))` with
   ASCII domains `UNICITY_EVM_RANDAO` / `UNICITY_EVM_BEACON`, `r` the authorizing
   root round and `n` the shard round.

5. **Certified round clock.** Deadlines compare the recorded certified root round
   against thresholds with `>=`, fire once even across skipped rounds, and reject
   any certificate that moves the recorded round backwards.

6. **Round types** genesis / successful / quiet / repeat / canceled each have a
   fixed `IR` shape and a fixed effect on the seal-registry cursors; a repeat
   never creates a second reward claim; a canceled attempt is never committed.

7. **v0 is deleted, not migrated.** No live deployment uses the prototype
   derivation. `F2` replaces `engineapi/params.go`'s derivation with v1.

## Deliverables

- `evmroot/` — independent executable model (own CBOR encoder, no bft-go-base
  dependency) and vector generator.
- `evmroot/testdata/vectors.json` — committed vectors, regenerated by
  `go run ./evmroot/cmd/d1vectors -update`, checked by `TestVectorsMatchGolden`.
- The design doc above — the normative profile text.

## Consequences

- `F1`/`F2` implement against a frozen profile with cross-checkable vectors
  rather than re-deriving from the prototype.
- The reth fork and any offline verifier get a language-neutral reference
  (`vectors.json`) to conform to.
- `engineapi/params.go` changes are breaking, but only relative to a prototype
  with no deployment, so no activation gate is needed for the change itself.
- D2 (reth system-call / fee profile) consumes `extraData`, `g_sys`, base-fee
  floor and gas accounting from here; D3 (weighted consensus) and D4 (epoch
  handoff) consume the `O_-` / `TE_-` / `D` shapes.

## Alternatives considered

- **Keep v0, document it.** Rejected: it has no `extraData` commitment and no
  signature-subset invariant, so it cannot support proven-mode verification or a
  second implementation.
- **Commit the whole certificate in `extraData`.** Rejected: CBOR re-encoding and
  signature-map ordering are not byte-stable across honest implementations; the
  signed `UnicitySeal.Hash` and a signature-free `O_-` are.
- **Use Keccak/RLP throughout for EVM-adjacent structures.** Rejected: the root
  input is a Unicity-consensus artifact; SHA-256/CBOR is the consensus layer's
  hash world and keeps the commitment independent of Ethereum trie encoding
  quirks.
