# Root handoff profile 2 (WP3 i-a)

Profile 2 is selected by `consensus.Parameters.NetworkProfileVersion`. Version 0 or 1 preserves the legacy block, payload, shard-state and recovery encodings. Profile 2 uses block and payload version 2, and adds one root-maintained `P_CTL = 0xFFFFFFFF` UnicityTree leaf with value `SHA256(ControlState.Bytes())`. The leaf uses the existing `UnicityTreeData` and indexed-tree hashing. P_CTL cannot be configured, registered, certified, or scheduled for a timeout as a shard.

The profile-2 payload carries at most one canonical ordered handoff record per block. Prepare, freeze, commit and abort advance the branch-local control state; the record's network, epoch, predecessor, attempt, kind and order round are checked during execution. A committed H fixes its order round and the successor identifiers. Subsequent old-epoch blocks must have an empty payload. The executor copies all shard and control state unchanged, without loading round-selected configurations or advancing shard epochs. The proposal and recovery paths both call `BlockStore.Add` before a vote or pending-block admission, which checks the authenticated parent branch before execution. Local leaders emit empty suffix payloads and stop scheduling shard timeouts, but admission remains the safety check.

Profile-2 persisted blocks and typed recovery checkpoints reconstruct the control leaf and compare the complete tree root with the committed root. A recovery checkpoint carries control data separately from ordinary ShardInfo. Fee and statistics accumulators are checked against their technical-record hashes; profile-2 epoch rollover refreshes those hashes without marking the shard changed or emitting a certificate. Subsequent empty commits clear the changed set, so they do not mint higher-round shard UCs.

`handoff/testdata/generate_old_commit_proof.go` independently encodes the control and QC bytes and signs with Decred secp256k1. The verifier fixes both the P_CTL path-item key and lookup key, recomputes the root, and checks a real weighted old QC(c+1). It must be supplied an independently authenticated old trust base and, when used with the handoff machine, the expected context. This i-a branch does not activate the successor committee or enable profile 2 in the CLI; typed bootstrap and activation belong to i-b.

## H3 addition: EVM assignment and the derived configuration

An assignment-bearing H still copies shard and control state unchanged through its old-epoch suffix. At the first new-root block the executor installs the successor EVM assignment from committed history: the configuration derived from the retained candidate must hash to what the commit record's `SuccessorTRHash` implies, or the checkpoint is refused. Orchestration holds a derived, idempotent index of those configurations keyed by activation round; startup repairs it from committed data before the block tree loads (`storage.New`, `reconcileAssignmentHistory`) and `initBlock` refuses a stored EVM shard whose configuration hash is not the derived one. See [h3-evm-assignment.md](h3-evm-assignment.md).
