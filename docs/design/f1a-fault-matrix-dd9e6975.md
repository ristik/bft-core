One clean run of the real-reth fault matrix at a single accepted integration head, measured to close
the two gaps the F1 acceptance ledger left open under #88, and to say precisely what it does not
close.

This is a measurement record. It closes nothing by itself: a ledger or a run written by the party
that did the work is a proposal for somebody else to check.

## 2. What a restored node did, and did not, do

The handoff asks that following and executing new certified work be distinguished from voting, and
that the limitation be mapped rather than glossed. The run measures the distinction directly.

Every restarted **shard process** logs `abstaining: restored process is non-voting`
(`shardnode/round.go:777`) for the rounds after it returns:

| scenario | restored-gate log messages | why |
|---|---|---|
| follower-restart | 10 | the shard process was restarted |
| leader-kill | 11 | same |
| pair-restart | 8 | same |
| reth-only-restart | **0** | only reth restarted; the shard process kept running, so it did not enter the restored-process gate; executor availability still gates voting |
| multi-leader | **0** | no restart |

So what these scenarios establish is that a restored node **follows the chain and executes new
certified work**. They do not establish restored signing, and the zero rows are what make that a
measurement rather than an assumption: the one scenario that did not restart a shard process is the
one with no restored-process abstention messages. This does not establish uninterrupted voting: executor-read failures still prevent that round from reaching a vote.

Restoring signing is #105 (F6c). Its step 1 and step 2 are merged (`4f0ec961`, `dd9e6975`); step 3
was open at the measured revision and subsequently merged as #142 (`3d75e55e`). Nothing in this
matrix measures that later integration or establishes restored signing.

## 3. Named refusals observed

| refusal | count | where | reading |
|---|---|---|---|
| `no-anchor` | 12 | pair-restart, validator 2 | the returning process holds no anchor, so it cannot name the certified block its executor must reach, and it refuses to build rather than guessing. It recovered once a non-quiet certificate arrived, which is what the scenario's later assertions record |
| `connection refused` on `eth_getBlockByNumber` | 36 | reth-only-restart | the shard process polling its own stopped reth. Expected while the executor is unavailable; these are failed head reads, not evidence that the node votes during the outage |
| `connection refused` on `eth_getBlockByNumber` | 3, 3, 4 | follower-restart, leader-kill, pair-restart | aggregate scenario-log counts; not individually attributed to the fault window |
| `/unicity/shard-payload/1.0.0` dial failures | a few per restart scenario | dissemination to the absent validator | expected while it is down |

`no-anchor` appearing only in pair-restart is the #92 shape: a process that restarts alongside its
executor holds no anchor, and a quiet tail gives it nothing that names a block. The design record is
`docs/design/f6b-quiet-tail-anchor-recovery.md`.

**Authenticated-evidence anchor recovery was off.** The harness starts shard nodes with no evidence
flags, so `cli/ubft/cmd/shard_node_run.go` defaults apply: `--evidence-serve=true`,
`--evidence-recover=false`. Recovery in these scenarios is therefore the ordinary path (reconcile to
the certified block once a non-quiet certificate names one, with the execution client acquiring
ancestors itself), **not** the authenticated-evidence lifecycle. This run is not evidence about that
lifecycle in either direction.

## 4. Evidence discipline

- every scenario archive was checked for `keys.json` and `jwt.hex` before sealing, and the check
  passed in all three runs;
- scan inputs were recorded per cluster and sealed **outside** the archive
  (`evidence-runs/.scan-inputs/<runID>.scan`), so a leaked secret in an earlier cluster cannot pass
  upload selection after that cluster is replaced;
- the collection path was exercised on purpose with `-F`. The injected failure produced exit 1, and
  the supervisor still sealed 23 artefacts and archived them. A passing run never proves this path;
- before committing the archives here they were independently re-checked: no entry named
  `keys.json`, `jwt.hex`, `*.key` or `secret`, no `privateKey`/`secretKey` field and no PEM private
  key block in any file. The workload's signing key is the universally known Hardhat/Anvil account 0,
  already public in `scripts/evmtx/main.go`, and it does not appear in any archive.

## 5. Reconciliation against the ledger's two open gaps

`docs/design/f1-acceptance-ledger.md` §2 named exactly two gaps under #88, both measurement rather
than repair.

| gap as written | status now |
|---|---|
| "Leader kill has no passing measurement at a current head" | **closed by measurement.** The leader-kill scenario passed at `dd9e6975`: the shard rotated past the killed leader, a transaction executed while it was absent, and the returning validator accepted a new certificate and executed new work, with head, nonce and 5 receipts agreeing across all four clients |
| "No full matrix has been run at the current merged head" | **closed by measurement.** All five scenarios ran at `dd9e6975` in one invocation under one manifest, plus baseline |

Both closures inherit the limitation #110 already stated and this record repeats: **each outcome is
a single run.** One passing run is not a claim that the failure cannot recur, and nothing here
supplies a repetition count or a flake rate.

## 7. Independent review of retained evidence

The reviewer checked all three committed archives against the corresponding sealed private per-run
scan records (36, 108 and 36 recorded values respectively), with no value matches. Filename,
private-key-field and PEM-marker checks also found no matches. The private scan records remain
outside the repository. This is artifact inspection, not another devnet run. The retained manifests
confirm a separate baseline invocation, one five-scenario matrix invocation, and a separate injected
failure invocation. Restored-gate counts above are log-message counts, not a claim of continuous
voting or a distinct-partition-round count.
